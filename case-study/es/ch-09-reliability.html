Capítulo 09

Redis Streams y DLQ

Entrega al-menos-una-vez, bucles de recuperación y letras muertas que dicen la verdad.

El trabajo pesado (informes LLM, SHAP, embeddings) ocurre fuera de la ruta de request a través de tres Redis Streams. Listas simples de Redis servirían como cola básica, pero los Streams traen la semántica que un pipeline financiero necesita:

  • Consumer groups: cada pool de workers lee independientemente con su propio offset — los mensajes llegan al-menos-una-vez y sobreviven crashes del consumidor.
  • Recuperación de pendientes: un loop corre XAUTOCLAIM cada 60s para reclamar mensajes atascados idle > 5 minutos (consumidores muertos), así nada se pudre sin que nadie lo vea.
  • Dead-letter queue: tras fallos repetidos los mensajes van a fraud:dlq estampados con stream original, grupo y motivo del error — los fallos se vuelven eventos inspectables, no trabajo perdido.
  • Memoria acotada: los streams se recortan en ~100K entradas (MAXLEN aproximado); la DLQ tiene tope de 10K.

El principio de diseño: la API siempre responde rápido; el enriquecimiento llega eventualmente; y cuando falla, el fallo mismo es un dato durable que un ingeniero puede reprocesar.

El paso de publicación es un problema de base de datos, no de Redis

Los consumer groups y el DLQ solo resuelven la entrega. No dicen nada sobre el instante entre "la transacción está puntuada y commiteada" y "los eventos están en el stream" — y ese instante es donde este pipeline solía perder trabajo.

El endpoint de scoring llamaba a publish_event tres veces, fire-and-forget, cada una envuelta en su propio try/except. Un tirón de Redis producía por tanto una transacción commiteada y totalmente puntuada sin informe LLM, sin atribución SHAP y sin embedding de merchant. El fallo sí se logueaba, así que nunca fue realmente silencioso — pero nada podía descubrirlo ni repararlo después: el endpoint de report devolvía pending para siempre y no existía ninguna query de reconciliación en el codebase.

La solución es un outbox transaccional. Cada evento se escribe como una fila en la misma transacción de base de datos que la transacción puntuada, así que commitea atómicamente con ella; un relay lo publica a Redis después. De ahí se siguen dos propiedades, y solo la segunda era obvia:

  • Durabilidad. Si la API muere entre el commit y la publicación, la fila sigue ahí para que alguien la recoja. El evento no puede perderse por un proceso que ya no existe.
  • Sin carrera pre-commit. Los eventos se publicaban antes del commit, porque el commit real ocurre en el teardown de get_db después de que el handler devuelve. Las tres tablas consumidoras tienen una foreign key dura a transactions.id, así que un worker que recogía el mensaje dentro de esa ventana de submilisegundos se topaba con una violación de FK y gastaba sus reintentos contra una transacción que estaba a punto de existir. Publicar estrictamente después del commit elimina la ventana por completo.

La lección trasciende a Redis: una vez que un pipeline hace fan-out a tres consumidores independientes, el traspaso es una transacción distribuida, y el único sitio honesto donde hacerla atómica es la base de datos que ya posee la verdad.
