01 · Context

Why Fraud Detection Is Hard

Card fraud is an adversarial, extremely imbalanced prediction problem. Three properties make it fundamentally different from a typical classification task:

Extreme class imbalance. In realistic datasets only ~1% of transactions are fraudulent. A model that predicts "legitimate" for everything achieves 99% accuracy and catches zero fraud. This is why the system is evaluated with F1 and per-tier thresholds, never raw accuracy.

Decisions must be explainable. When a transaction is blocked, an analyst — and sometimes a regulator — needs to know exactly why. A bare probability from a black-box model is not acceptable in financial environments.

Fraud adapts. Patterns that work today decay as fraudsters change tactics. A static model silently degrades, which is why drift monitoring and retraining triggers are part of the architecture, not an afterthought.

Design consequence

No single technique covers all three constraints. The answer chosen here is a hybrid: deterministic rules for transparency, ML for pattern discovery, and infrastructure that keeps both honest over time.

02 · Overview

Architecture: Three Layers, One Score

Every transaction flows through three independent scoring layers. Their outputs are combined into a single 0–100 risk score:

risk_score = 0.60 × rule_score + 0.25 × ml_score + 0.15 × context_score
// weights configurable via environment, no retraining needed to tune

The final score is compared against a dynamic threshold (Section 5) to classify each transaction as legitimate, review, or fraud. Flagged transactions are persisted and pushed to async workers that enrich them with LLM reports, SHAP attributions and merchant embedding analysis — without ever blocking the API response path.

03 · Layer 1

The Rule Engine: Transparent by Construction

Before any machine learning runs, nine deterministic rules evaluate the transaction. Each rule encodes a known fraud pattern with an explicit weight; fired rule weights are summed and capped at 100.

Why rules at all? Rules run in microseconds, never fail silently, and produce a human-readable justification for free ("triggered: high_amount + off_hours_crypto"). They also cover cold-start scenarios where no ML model exists yet — the system scores meaningfully from day zero with ml_score = 0.

Risky categories: btc, crypto, gambling, casino, money_transfer.

Note how the weights encode domain logic: amount alone (35) outweighs odd timing alone (10), but night-hour crypto activity (25) jumps near the top because the combination is far more suspicious than either factor individually. These numbers are tunable configuration — analysts can recalibrate risk policy without touching code or retraining anything.

04 · Layer 2

XGBoost on Ten Engineered Features

The ML layer learns what rules cannot express: non-obvious combinations of amount, rhythm, geography and category that separate fraud from legitimate spending.

Feature engineering: where the domain knowledge lives

Raw inputs (amount, timestamp, merchant) are transformed into ten features that expose behavioral signal to the model:

FeatureWhat it captures
amountraw transaction amount
amount_vs_user_avghow many times larger than this user's average spend
amount_vs_user_stdz-score vs the user's spending deviation — "is this abnormal FOR THIS USER?"
tx_count_last_5minburst velocity, 5-minute window
tx_count_last_1hsustained velocity, 1-hour window
hour_of_daytemporal position — fraud concentrates at night
is_weekendweekend flag — spending patterns differ
merchant_risk_levelhigh-risk category flag (crypto, gambling…)
is_cryptocryptocurrency flag — irreversible payments
amount_round_numberround amounts correlate with manual testing of stolen cards

The relative features (amount_vs_user_avg, _std) matter most: $2,000 is unremarkable for one user and alarming for another. Normalizing against each user's own baseline lets a single model serve everyone.

Why XGBoost?

  • Supervised signal: trained on labeled fraud (~1% prevalence), it optimizes directly for separating the classes — unlike anomaly detectors such as Isolation Forest, which only know "this looks unusual".
  • CPU-friendly latency: tree inference is microseconds — compatible with real-time scoring, no GPU serving infra needed.
  • SHAP-native: its tree structure plugs directly into TreeExplainer for exact per-prediction attributions (Section 6).
  • Tabular king: on small-to-medium tabular data, gradient-boosted trees remain the state of the art versus deep learning.

Taming the probability curve

XGBoost's raw probability is compressed toward 0.5 under class imbalance. The system applies a cubic smoothing before scaling to 0–100, so only confident predictions score high while mid-range uncertainty stays mid-range instead of producing false alarms:

smoothed = 0.5 + 0.7 × (p − 0.5)³ + 0.3 × (p − 0.5)
ml_score = clip(smoothed, 0, 1) × 100

If the model file is missing, the layer returns ml_score = 0 and the system keeps scoring with rules + context. Degradation is explicit, never a crash.

Inside the trained artifact

The production model is a serialized XGBClassifier whose own hyperparameters tell the imbalance story:

HyperparameterValueWhat it means
n_estimators500boosted trees in the ensemble
max_depth6interaction depth kept shallow against overfitting
learning_rate0.1conservative step size per tree
subsample0.8row sampling per tree — built-in randomness
scale_pos_weight≈ 99.8one fraud example weighs like ~100 legitimate ones — the mathematical answer to class imbalance

Training discipline

  • No leakage: SMOTE oversampling is applied strictly on the training split, never before it.
  • Realistic noise injection: fraud amounts get ±15% variance, 3% of fraud merchants receive name typos, timestamps jitter ±30 min — deliberately teaching the model that fraudsters don't repeat exact patterns.
  • Stratified splits: the ~1–5% fraud ratio is preserved across train/test.
  • Cost-sensitive evaluation: a missed fraud (false negative) is priced at 10× a false alarm, and the decision threshold is chosen to minimize expected economic cost rather than raw accuracy.
05 · Decision Policy

Dynamic Thresholds: Risk Depends on Amount

A fixed cutoff would be wrong: blocking every $50 transaction above score 45 would drown analysts in false positives, while waiting for score 70 on a $60,000 transfer would be negligent. The decision threshold therefore scales inversely with amount:

Amount TierFraud Threshold
$0 – $1,000≥ 70
$1,001 – $10,000≥ 50
$10,001 – $50,000≥ 45
$50,001+≥ 40

The intuition: the more money moves, the less certainty you demand before acting. Scores between 75% of the tier threshold and the threshold itself land in a review band — flagged for human analysis rather than auto-blocked. This band is where the human-in-the-loop design lives: the system narrows thousands of transactions down to a reviewable queue, and analysts make the final call.

Why not let ML decide alone?

The ensemble deliberately gives rules the largest weight (0.60). When an analyst asks "why was this blocked?", the answer often starts with a named, weighted rule — auditable logic — reinforced by model evidence. Pure-ML blocks are harder to defend and impossible to tune surgically.

06 · Explainability

SHAP: Attributing Every Prediction

A score says how much risk; SHAP says which features caused it. SHAP (SHapley Additive exPlanations) borrows from cooperative game theory: each feature is a player, the prediction is the payout, and Shapley values split the credit fairly across features according to their marginal contribution over all possible feature orderings.

In practice, the system runs TreeExplainer — an exact, polynomial-time SHAP algorithm specialized for tree ensembles — asynchronously after each scored transaction, and persists the top-5 contributions by absolute value, expressed in log-odds: the model's raw additive scale, before any sigmoid converts it into a probability. The React dashboard renders these as attribution cards.

This closes the loop between layers: rules give named triggers, SHAP gives feature-level causes, and together they turn a black-box score into a defensible narrative. Attributions are computed in a dedicated worker precisely so explanation cost never sits on the scoring request path.

07 · Network Signal

Fraud Rings: Because Fraud Is Social

Fraudsters rarely act alone — stolen cards get resold through shared mule accounts and reused merchant endpoints. Individual scoring misses this; graph analysis does not.

The system maintains a directed graph (NetworkX) whose edges connect users to merchants and cards they touch. From this structure it derives:

  • Fraud proximity: if a user transacts within ≤ 2 hops of a known fraudster, the near_fraud rule fires (+15).
  • Degree centrality: unusually connected nodes surface as coordination hubs worth reviewing.
  • Automatic hygiene: nodes older than 30 days are pruned (known fraudsters are preserved) so the graph stays bounded and current.

This is a second-order feature: it captures relationships that neither rules nor per-transaction ML can see, because the signal lives between entities, not inside one transaction.

08 · NLP Signal

Catching Lookalike Merchants with Embeddings

A classic fraud trick is impersonation: register as AMAZ0N_STORE or Amaz0n Payments and hope string-matching blacklists miss the typo. Exact and character-distance matching catch some cases but fail systematically against deliberate substitution.

Instead, merchant names are embedded with sentence-transformers (all-MiniLM-L6-v2) and compared against ten trusted merchant names using cosine similarity. Names scoring above 0.85 similarity to a trusted brand — without being that brand — are treated as likely spoofs and feed the merchant-risk signal.

Semantic embeddings understand that AMAZ0N_STORE sits "close" to Amazon in vector space even though the strings barely share characters. The computation runs in its own async worker and caches results in Redis with a 1-hour TTL, keeping the hot path clean.

09 · MLOps

Drift Monitoring: Models Decay Silently

A deployed model doesn't announce when it stops working. User behavior shifts, fraud tactics evolve, and accuracy bleeds out month by month. Two complementary detectors watch for this:

  • Data drift (Evidently): compares current feature distributions against a reference window. If tx_count_last_5min suddenly looks nothing like training data, predictions become unreliable even before labels say so.
  • Custom PSI: a hand-rolled Population Stability Index provides a lightweight, dependency-free sanity check on the same distributions.

Detection is paired with action. Retraining triggers fire automatically when either:

F1 < 0.7  // quality floor
drift_score > 30  // distribution alarm

This converts model maintenance from "someone notices someday" into an observable, testable condition — the difference between an ML demo and ML in production.

10 · Infrastructure

Redis Streams: At-Least-Once, Recoverable, Auditable

Heavy work (LLM reports, SHAP, embeddings) happens off the request path through three Redis Streams. Plain Redis lists could do naive queuing, but Streams bring the semantics a financial pipeline needs:

  • Consumer groups: each worker pool reads independently with its own offset — messages are delivered at-least-once and survive consumer crashes.
  • Pending recovery: a loop runs XAUTOCLAIM every 60s to reclaim messages stuck idle > 5 minutes (dead consumers), so nothing rots unseen.
  • Dead-letter queue: after repeated failures messages move to fraud:dlq stamped with original stream, group and error reason — failures become inspectable events, not lost work.
  • Bounded memory: streams trim at ~100K entries (MAXLEN approximate); the DLQ caps at 10K.

The design principle: the API always answers fast; enrichment arrives eventually; and when enrichment fails, the failure itself is durable data an engineer can replay.

11 · Trust

Security, Roles and an Immutable Trail

A fraud system is itself a target. Baseline hardening includes:

  • JWT lifecycle: short-lived access tokens (15 min), refresh tokens, and server-side blacklist on logout — stolen tokens expire fast and die explicitly.
  • Role-based access: analysts query and review; only admins soft-delete transactions, export audit logs, or inspect analyst activity.
  • Rate limiting: login/register 10/min, transactions 100/min, alerts 60/min — credential-stuffing gets expensive.
  • SHA-256 audit chain: every score, analyst review and LLM report lands in an append-only log with checksums, making tampering detectable.
  • Soft delete: transactions are flagged, never physically erased — financial history stays queryable for audit and future retraining.

13 · Honesty

Limitations & Next Steps

A case study that hides its gaps is marketing, not engineering. Known limitations, stated plainly:

  • No published held-out metrics yet. Figures 2 and 3 come from the model's own training dataset, so their separation is optimistic. The immediate next step is a reproducible evaluation split reporting honest F1 / PR-AUC on unseen transactions.
  • Synthetic data provenance. The current artifact trains on generated transactions (with a PaySim mapping path available). Real-world claims require real labeled traffic — by design, the pipeline is dataset-agnostic.
  • Bounded score range. The cubic serving curve compresses ml_score into roughly [26, 74] — the medians in Figure 2 sit exactly on those bounds. A deliberate calibration trade-off worth revisiting only if finer granularity near the extremes is ever needed.
  • Screenshots pending deployment. The analyst dashboard exists and is tested; this page will embed real UI captures once the demo runs publicly.

Each of these has a concrete owner and plan — which is exactly what separates an honest roadmap from a wish list.
