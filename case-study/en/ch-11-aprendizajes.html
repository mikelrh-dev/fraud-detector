Chapter 11

Learnings and Limitations

Honest reflections, known gaps and what comes next.

What building this taught me

  • Feature engineering beats model complexity. The relative features (amount vs each user's average and deviation) carry the personalization signal — raw amount alone is nearly meaningless until normalized against a baseline.
  • Class imbalance is a math problem, not a mystery. But the ratio Cfn/Cfp is a business fact you are handed, not one you can derive. evaluate_cost.py sweeps it from 1× to 500× precisely because no single value is defensible, and the optimal threshold moves two orders of magnitude across that range (Chapter 4). Quoting one number would have been an assumption wearing a decimal point. Lesson: when a threshold is a business decision, make the script show the whole sweep and refuse to pick the row.
  • The hard part is usually the data, not the model. Every dramatic "the model is broken" moment in this project turned out to be the corpus lying: an amount distribution arranged so that the largest transactions were mostly legitimate, which the model learned faithfully and inverted; per-class velocity windows disjoint enough that tx_count_last_5min became a sufficient statistic for the label; a category field where cripto and crypto-exchange silently zeroed is_crypto. In each case the fix was to the generator or the vocabulary, and the metric moved afterwards. Lesson: before tuning, check whether the data is telling you something true.
  • Class weighting has to be derived, not assumed. scale_pos_weight is now computed from the un-resampled training split — 39,598 legitimate ÷ 402 fraud = 98.50 — and the artifact stamps the prior its calibrator actually saw (0.010050). The value follows the corpus; it is never typed in. Lesson: a hardcoded class-weight constant is a silent claim about a base rate that nobody re-verifies.
  • Explainability is a product feature. SHAP attributions changed how alerts get reviewed: analysts trust a score that shows its work.
  • Reliability is an architecture decision. Consumer groups, pending-message recovery and a dead-letter queue separate "usually works" from an auditable pipeline.
  • The LLM belongs after the decision. Keeping report generation asynchronous and strictly non-decisive removed the scariest failure mode from day one.

What I would do differently

  • Publish held-out metrics from week one — evaluation debt compounds silently.
  • Deploy the demo before polishing documentation this far; a running system teaches faster than any diagram.
  • Chase real labeled traffic earlier. Synthetic data got the architecture right but cannot prove production F1.

Known limitations

A case study that hides its gaps is marketing, not engineering. Known limitations, stated plainly:

  • No evaluation on real traffic yet. Held-out metrics do exist and Chapter 4 publishes them in full — PR-AUC 0.7740, 29 frauds missed out of 100, and a per-archetype error breakdown — but they measure self-consistency against a corpus written by the same person who wrote the features. The score-distribution figure additionally comes from the model's own training dataset, so its separation is optimistic relative to unseen traffic. What remains open is a reproducible evaluation on real labelled traffic reporting honest F1 / PR-AUC on transactions the model has never touched.
  • Synthetic data provenance. The current artifact trains on generated transactions (with a PaySim mapping path available). Real-world claims require real labeled traffic — by design, the pipeline is dataset-agnostic.
  • A score with no useful middle. Because the calibrated probability goes to the score unscaled by any post-processing, the distribution is close to bimodal: only 0.4101% of legitimate traffic scores inside [20, 80] while the fraud median sits at 87.2499, so almost no mass lands between the two. That is fine for ranking and terrible for reading a single number — a transaction scoring 3 and one scoring 17 are both simply "low". Ranking quality and score resolution are separate problems, and only the first is solved here.
  • Screenshots pending deployment. The analyst dashboard exists and is tested; this page will embed real UI captures once the demo runs publicly.
  • Hyperparameter search not yet systematic. Current parameters are hand-tuned with regularization judgment (Chapter 3 states this plainly); a randomized/Optuna study over the documented search space is queued.
  • Benchmarks pending a running deployment. Scoring-endpoint latency percentiles, per-rule false-positive rates and a fairness audit across segments require live labeled traffic — they are first-class roadmap items, not afterthoughts.

Each of these has a concrete owner and plan — which is exactly what separates an honest roadmap from a wish list.

docker compose exec api python scripts/init_db.py
docker compose exec api python scripts/seed_demo_data.py
