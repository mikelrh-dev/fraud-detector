Chapter 09

Redis Streams and DLQ

At-least-once delivery, recovery loops and dead letters that tell the truth.

Heavy work (LLM reports, SHAP, embeddings) happens off the request path through three Redis Streams. Plain Redis lists could do naive queuing, but Streams bring the semantics a financial pipeline needs:

  • Consumer groups: each worker pool reads independently with its own offset — messages are delivered at-least-once and survive consumer crashes.
  • Pending recovery: a loop runs XAUTOCLAIM every 60s to reclaim messages stuck idle > 5 minutes (dead consumers), so nothing rots unseen.
  • Dead-letter queue: after repeated failures messages move to fraud:dlq stamped with original stream, group and error reason — failures become inspectable events, not lost work.
  • Bounded memory: streams trim at ~100K entries (MAXLEN approximate); the DLQ caps at 10K.

The design principle: the API always answers fast; enrichment arrives eventually; and when enrichment fails, the failure itself is durable data an engineer can replay.
