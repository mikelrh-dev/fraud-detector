Chapter 02

The Rule Engine

Deterministic, transparent, tunable — the layer that makes every decision defensible.

Before any machine learning runs, seven deterministic rules evaluate the transaction. Each rule encodes a known fraud pattern with an explicit weight; fired rule weights are summed and capped at 100.

Why rules at all? Rules run in microseconds, never fail silently, and produce a human-readable justification for free ("triggered: high_amount + off_hours_crypto"). They also cover cold-start scenarios where no ML model exists yet — the system scores meaningfully from day zero with ml_score = 0.

RuleWeightTrigger
high_amount35–60amount > $1,000, plus 8 per order of magnitude above it
velocity_burst30> 1 txn in 5 min in a risky category
high_velocity25> 3 txns in 5 minutes
off_hours_crypto25night hours (00–06) + adversarial category
unusual_merchant20blacklisted merchant, adversarial category or merchant name, or regulated category with corroboration
near_fraud15user ≤ 2 hops from a known fraudster (graph)
unusual_hours10transaction between 00:00–06:00

Adversarial (fire on their own): cryptocurrency, crypto, btc, gambling, casino, adult. Regulated (need a second signal): money_transfer, pharmacy. Risky, for velocity_burst: those eight together.

That split is the point. Flagging a transaction purely because it happened at a pharmacy or a remittance provider is a false positive by construction, so a regulated merchant only scores when velocity, a night hour or a blacklist entry corroborates it. A casino is different — the category itself is the claim, so it stands alone. Corroboration for a regulated merchant means velocity (> 1 txn in 5 min), a night hour (00–06) or a blacklisted merchant name.

Note how the weights encode domain logic: amount alone (35 base, up to 60 at the ceiling) outweighs odd timing alone (10), but night-hour crypto activity (25) jumps near the top because the combination is far more suspicious than either factor individually. These numbers are tunable configuration - analysts can recalibrate risk policy without touching code or retraining anything.

high_amount is the one rule whose weight depends on the transaction, and it is worth being explicit about why. As a switch it scored 1,001 and 400,000 identically, so a quarter of a bitcoin at an exchange and a coffee were the same evidence - and a real 400,000 USD transaction at binance came out at 24.1/100, "legitimate". It now weighs 35 + min(8 × log10(amount / 1000), 25): 35.33 at 1,100, 43 at 10,000, 55.82 at 400,000. The +25 ceiling is derived rather than chosen. The strictest amount tier thresholds at 40, so a rule score above 66.67 reaches fraud by itself on a critical-tier amount; below 50,000.01 that same evidence is downgraded to review for an analyst instead of a block. The ceiling keeps one rule from spending the whole scale on its own and collapsing the difference between "suspicious" and "clearly fraud".

That transaction failed for a second reason as well. merchant_category said retail, so the two features that know what kind of merchant this is - merchant_risk_level and is_crypto - were both 0.0, and the merchant's own name was never consulted by anything. Both engines now read merchant_name through one shared vocabulary, matched by token and case-insensitively: binance matches "Binance Exchange", "BINANCE.COM" and "Binance Berlin", while "BinanceCard" and "PreBinance" do not. A name hit resolves to a category and goes through the same tier test above, so it can only raise the risk, never lower it.

One vocabulary, not three

Every category check in this project — velocity_burst, off_hours_crypto, the adversarial/regulated tiers above, the feature engine's merchant_risk_level and is_crypto, and the training generator — used to consult its own private list of category names. Three disjoint vocabularies in one codebase is not a style problem: it means the rule layer and the feature layer can disagree about whether the same transaction is crypto, and they will both be right about their own table.

They now share src/core/ml_constants.py. The interesting part is what happened when they started agreeing. merchant_category is free text on the wire, so real traffic contains cripto, crypto-exchange, Crypto Exchange and forty-odd other spellings of the same idea. The rule engine's two-entry lookup missed them and simply did not fire; the feature engine looked them up in a table whose keys were stored normalized, so any spelling carrying a separator, a space run or a capital missed it entirely and fell through to the default — input unchanged. The result was a crypto exchange transaction that silently scored is_crypto = 0, and the model trained on that.

The shared module resolves all of it through one normalize_category backed by a 46-entry alias table, and the fix is load-bearing rather than cosmetic: an unknown_merchant_category counter increments on every value that matches nothing, so the log names exactly which strings need adding. Unknown values now score the risk features at zero and announce themselves, instead of passing for a category that genuinely is not risky.

The training side closes the loop deliberately. ALIAS_SPELLING_RATE = 0.15 means 15% of high-risk rows are written with an alias spelling rather than the canonical name, so the artifact is never trained inside a cleaner input distribution than production supplies. The generator also publishes an inversion of the alias table — mapping canonical name to its alternate spellings — because looking up a canonical name in a table keyed by alias returns nothing, which is how an entire emission branch ends up described in a comment and never executed.
