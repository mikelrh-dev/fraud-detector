Chapter 10

Security and Audit

Hardening the system that hunts fraud.

A fraud system is itself a target. Baseline hardening includes:

  • JWT lifecycle: short-lived access tokens (15 min), refresh tokens, and server-side blacklist on logout — stolen tokens expire fast and die explicitly.
  • Role-based access: analysts query and review; only admins soft-delete transactions, export audit logs, or inspect analyst activity.
  • Rate limiting: eight Redis fixed-window counters keyed by client IP and path prefix, matched most-specific-first so the /auth/* entries are not shadowed by the broader ones. Per 60 seconds: login 10 · register 10 · refresh 5 · logout 20 · transactions 100 · alerts 60 · audit 60 · monitoring 30. Credential stuffing gets expensive, and so does an audit-export or monitoring-poll loop — both of which are read-heavy enough to be worth metering on their own. The limiter fails open if Redis is unreachable, which is a deliberate availability-over-strictness trade and is logged when it happens.
  • Per-row SHA-256 checksums: every score, analyst review and LLM report lands in an append-only audit_entries log, and each row carries a SHA-256 checksum over its own canonicalised content, with keys sorted so the digest is deterministic. This detects modification of a logged row — an edited decision, a doctored review outcome. It is not a hash chain: there is no prev_hash column, so a row that is deleted or reordered leaves no trace, and the guarantee stops at "this row has not been altered since it was written". Pair it with the database's own append-only privileges and retention policy for the deletion case.
  • Untrusted input at the rule layer: amount and merchant_name arrive as raw values, so amount > 1000 raises TypeError on a string and .lower() raises AttributeError on a non-string. Pydantic protects the HTTP path, which is exactly why this stayed invisible — every other consumer (batch import, replay tool, future queue worker) inherited a crash. Absent and present-but-malformed are now distinguished on purpose: a value that is present and unusable is treated as untrusted input and fires high_amount, because coercing it to zero would let anyone who can make the amount unparseable dodge every rule; a field that is simply absent keeps the old meaning of zero, so partial batch records do not flood the queue with false positives.
  • Soft delete: transactions are flagged, never physically erased — financial history stays queryable for audit and future retraining.
